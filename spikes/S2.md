# S2: PASS

S2 passed twice, on two different stores. **On ACA it passed on Azure Files NFS (`nfs4`). On AKS it
passed on an Azure Disk (ext4), which is the store the platform uses after the AKS decision.**
The NFS result is kept as evidence of the first design; it no longer describes the deployed data store.

| Run | Platform and store | `fstype` | `git status` | `worktree add` | build and commit (3,000 files) | 100x `os.replace` | torn/missing reads | `flock` | Result |
|---|---|---|---|---|---|---|---|---|---|
| 1 | ACA, Azure Files NFS (Premium, 100 GiB, NoRootSquash) at `/data` | `nfs4` (vers=4.1) | 0.148 s | **64.07 s** | **109.42 s** | 5.89 s (195 reads) | 0 | excludes; released on kill | PASS |
| 1 ref | ACA, container overlay (`/tmp/spike-s2`) | `overlay` | 0.025 s | 0.16 s | 0.48 s | 0.04 s (1,832 reads) | 0 | ok | PASS (reference) |
| 2 | **AKS, Azure Disk (CSI, Premium, ext4, RWO, 128 GiB) at `/data`** | `ext4` (`rw,relatime,idmapped`) | 0.017 s | 0.11 s | 0.38 s | 0.44 s (26,363 reads) | 0 | excludes; released on kill | **PASS** |
| 2 ref | AKS, container overlay (`/tmp/spike-s2`) | `overlay` | 0.023 s | 0.15 s | 0.47 s | 0.04 s (1,911 reads) | 0 | ok | PASS (reference) |

Both runs: ownership as the `factory` identity (uid 10001, new files 10001:10001 mode 0644), exec bit
and symlinks kept through git and directly, `git status` clean and sees a modification, worktree
removed. The pass criterion in `spikes/README.md` (the first run exits 0 with `"pass": true`, and
`git_status_seconds` at most 10 s) holds for both.

## The nfs4 criterion applies to the ACA run only

`spikes/README.md` requires `mount.fstype` of the first run to read `nfs4`. That is the ACA run
(run 1). It does **not** apply to the AKS run, because **NFS cannot be used on AKS with the accepted S1
pod**: S1 needs `hostUsers: false` (for `procMount: Unmasked`, see `S1.md`), and a pod with
`hostUsers: false` cannot mount an Azure Files NFS volume. Observed on the AKS spike cluster
(Azure Files CSI driver, protocol `nfs`, Premium, NoRootSquash share) with the pod of the S1 final
configuration:

```text
runc: failed to set MOUNT_ATTR_IDMAP on .../volumes/kubernetes.io~csi/pvc-<<PVC_ID>>/mount: invalid argument
```

runc applies an ID-mapped mount to every volume of a pod with its own user namespace, and NFS has no
support for it, so the pod never starts. Hence the **Azure Disk is the data store on AKS**. A disk does
support ID-mapped mounts (the mount options in run 2 show `idmapped`), and S2, S3 and S3b all
pass on it. Azure Files over SMB was not tried on AKS and is excluded by the design: it offers
mandatory locks only and its ownership is fixed at mount time, which the uid split
cannot use.

What the disk changes, in one place: it is ReadWriteOnce, so exactly one
replica, strategy `Recreate`, one zone, no sharing between pods.

## Call-outs

- **`git worktree add` took 64.07 s on NFS against 0.16 s locally, and the 3,000-file build and commit
  109.4 s against 0.48 s** (run 1). `git status` itself was fast (0.148 s, 5.9x the local figure, under
  the 10x guide of `spikes/README.md`, so it is not a failure). The first design would have paid
  about a minute for every worktree of a 3,000-file repository; the disk removes that cost
  (0.11 s).
- `os.replace` is about 10x slower on the AKS disk than on overlay (0.44 s against 0.04 s for 100 rounds),
  with a far larger number of concurrent reads (26,363), and no torn read. There is no pass
  threshold for it; recorded because it is the one figure where the disk is clearly worse than overlay.
- The pass criterion's optional step, one real `git worktree add` of `<<SANDBOX_TEST_REPO>>` on the
  mount, was **not run** on either platform.
- The `s2_*_exit` echoes of the raw captures are invalid (a quoting error in the capture commands) and
  are omitted. The result is read from `"pass": true` in each report, which `s2_nfs.py` returns as its
  exit status (0 on pass).

## Not covered

- A restart or reattach of the disk, a node replacement, and zone failure were not exercised.
- Throughput under four concurrent agents was not measured; S2 is a single-process correctness and
  latency check.
- The disk was attached to one pod at a time; ReadWriteOnce was not tested for what happens with a
  second pod (it is excluded by design: one replica, `Recreate`).
