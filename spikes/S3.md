# S3: PASS

S3 (the UID split with ambient capabilities) and S3b (the data-tree permission scheme with real ids on
the data store) passed on **both** platforms: on ACA with the data store on Azure Files NFS (`nfs4`), and
on AKS with the data store on an Azure Disk (`ext4`), the pod in the accepted S1 configuration
(`hostUsers: false`, `procMount: Unmasked`, AppArmor `Unconfined`; see `S1.md`). The `--mechanism none`
baseline FAILED on both platforms, as it must: it proves that the test can see the problem there.

| Check | ACA | AKS |
|---|---|---|
| S3 `--mechanism none` (baseline, must FAIL) | **FAIL**, exit 1: worker kept `CapEff e0`; `setuid` to the supervisor and to root **succeeded**; private directory listable | **FAIL**, exit 1 (`command terminated with exit code 1`): the same five checks failed |
| S3 default (what Factory does, must PASS) | **PASS**, exit 0 | **PASS** (`"pass": true`, empty `failed`) |
| S3b data tree on the data store | **PASS**, exit 0, `fstype` `nfs4` | **PASS**, `fstype` `ext4`, `"pass": true` |
| S3b reference run on local disk | PASS, exit 0, `fstype` `overlay` | not recorded |

The `--mechanism none` failures, identical on both platforms: `worker_has_no_caps`,
`worker_cannot_change_identity`, `worker_cannot_list_private_dir`, `worker_writes_shared_dir`,
`supervisor_reads_worker_file`. With the default mechanism the worker has uid 10002, gid 10010, no
supplementary groups and `CapPrm/CapEff/CapAmb` all `0000000000000000`; every `os.setuid`/`os.setgid`
attempt raises `PermissionError`; it cannot read `/proc/<supervisor pid>/environ` nor any other readable
`environ` holding the canary; it cannot list the supervisor's private directory; it writes the setgid
shared directory; and the supervisor reads what it wrote and can SIGKILL the worker's process group
(`CAP_KILL`). The supervisor holds exactly `CapAmb 00000000000000e0` and `NoNewPrivs 1`.

S3b, all 14 checks `ok: true` in all three runs: the worker has exactly (10002, 10010) with no
supplementary groups; `git status`, `git log` and `git cat-file` work in the worktree (through
`safe.directory` in the per-invocation `HOME`) and through the shared git directory; the worker cannot
list or read the clone, its working files, the run state file or the run directory; its own files are
visible to git; the supervisor reads them, runs `git status` on the worker's worktree, fetches into the
shared clone and adds a second worktree; new files stay in group 10010; the exec bit is kept. The
`agent_exit` value `RuntimeError: agent produced no result event` is the stub agent, by design
(S3b has no Anthropic key and no network).

## The nfs4 criterion of S3b applies to the ACA run only

`spikes/README.md` requires `"fstype": "nfs4"` for the S3b run. That is the ACA run. On AKS the NFS volume
cannot be mounted by a `hostUsers: false` pod (the `MOUNT_ATTR_IDMAP` error recorded in `S2.md`), so
the same scheme was proven on the Azure Disk (`ext4`), which is the data store there. A run on any
other file system does not count for the ACA question; for the AKS decision the ext4 run is the one
that counts, and it passes.

## Not covered

- S3 ran on the nodes and image above only. It exercises `Popen(user=)` with ambient `CAP_SETUID`,
  `CAP_SETGID` and `CAP_KILL`; the results on AKS with `hostUsers: false` are the same as on ACA.
- S3 does not test the Key Vault delivery half of the secrets design (secrets-store CSI driver, workload identity,
  the synced Kubernetes Secret): nothing in the spikes mounted a vault secret. That path is unverified
  until the first apply.
- No local-disk reference run of S3b was recorded on AKS.
