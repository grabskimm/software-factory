## The three relaxations that S1 PASS depends on

All three were needed together in the combinations tried (found by elimination, table above; not tried:
`hostUsers: false` alone, and `hostUsers: false` + `appArmorProfile: Unconfined` without `procMount`). They apply to the
Factory pod only; **Factory's own sandbox is not weakened**: no `enableWeakerNestedSandbox`, no
change to `managed-settings.json`, no extra capability, `no_new_privs` stays set, the worker still
holds no capability, and `failIfUnavailable` stays on (part 2 ran the real `claude` CLI with the
settings Factory generates).

1. `spec.hostUsers: false` (the pod gets its own user namespace). Kubernetes requires it for
   `procMount: Unmasked`. Side effect found by the follow-up work: a pod with `hostUsers: false`
   cannot mount NFS volumes (see `spikes/S2.md`).
2. `securityContext.procMount: Unmasked` on the container (the container runtime no longer masks or
   makes read-only parts of `/proc`). `bwrap` failed with "Can't mount proc on
   /newroot/proc: Operation not permitted" in the Azure Linux AppArmor-only run (no `procMount`, no
   `hostUsers: false`) and in the Kata run; the run that added `procMount: Unmasked` also added
   `hostUsers: false` (a requirement of the setting), so the error going away is not attributed to
   `procMount` alone.
   Why the kernel refuses a new procfs mount while `/proc` is partly masked is the usual
   explanation, but it was not separately proven here.
3. `securityContext.appArmorProfile.type: Unconfined` on the container. The default
   `cri-containerd.apparmor.d` profile (in `enforce` mode on the Ubuntu and Azure Linux runc pools; not in the raw captures) makes `bwrap`
   fail with "Failed to make / slave: Permission denied", even with `hostUsers: false` and
   `procMount: Unmasked` (run "default AppArmor" above).

The relaxations apply to the Factory pod only and are the price of running bubblewrap inside a pod; each
deployment must accept them knowingly.

**Kata (pod sandboxing) cannot work.** With the default pod it gets as far as user and mount
namespaces and then fails on the proc mount ("Can't mount proc on /newroot/proc: Operation not
permitted"; the likely cause is masked `/proc` paths in the guest container, not proven).
`procMount: Unmasked` needs `hostUsers: false`, and the Kata RuntimeClass refuses it: the pod
cannot start ("RuntimeClass handler kata does not support user namespaces"). So Kata can never get
the setting that part 1 needs.

## Not covered, and things that surprised us

- **The kernel's `Seccomp` field is 0 in every AKS capture** (no seccomp filter; the Kubernetes default
  without `seccompProfile`). On ACA it was 2 with one filter. Whether `seccompProfile: RuntimeDefault`
  would still let `bwrap` run on AKS was **not tested**; do not add it to the Deployment without
  re-running S1.
- S1 was run on a Free-tier spike cluster with D4ds_v5 nodes and Kubernetes 1.36.4. A node image or
  Kubernetes upgrade can change the AppArmor profile or the runtime; the result is tied to the versions
  above. Re-run S1 after such an upgrade.
- The Ubuntu pool was not tried with the relaxations; the production design uses Azure Linux 3.
- The early `rc=` / `*_exit=` echoes in some raw captures are invalid (a quoting error in the capture
  commands). They are omitted from the captures in this file. The S1 exit codes quoted here come from
  the scripts' own lines (`s1_bwrap_exit`, `sandbox_check_exit`, `command terminated with exit code 1`)
  and from the printed verdicts (`S1 FAIL`, `20 failed`, `all expectations held`).
- Nothing here exercises the Claude Code sandbox against the real Anthropic API or a real repository:
  part 2 uses a fake Messages API on localhost, as `spikes/README.md` specifies.
